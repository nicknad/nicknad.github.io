Building pwsafe: DPAPI, the clipboard, and Windows as the root of trust

September 16, 2026 · 7 min read

I built pwsafe to learn the Windows security surface the way otel-sqlite taught me OTLP: by forcing real constraints instead of tutorials. It is a Windows-only command-line password safe. pwsafe add github generates a password, stores it in a single vault file, and copies it to the clipboard; pwsafe get github copies it again. No master password, no daemon, and no command ever prints a secret to the terminal.

Windows is the root of trust

The usual password safe design wraps a vault key with a master passphrase you have to remember, type often, and never reuse. I went the other way: the vault is encrypted with the Windows Data Protection API under the current user. That makes the security boundary the Windows account itself, nothing more and nothing less. It removes the most phishable, most reusable secret from the picture entirely, at the cost of portability. The vault is bound to this user and this machine; it cannot be decrypted elsewhere, and there is no recovery path. It is honest about where the trust sits instead of pretending a second password fixes it.

DPAPI is the whole crypto story

The vault is DPAPI-encrypted JSON. Writing uses CryptProtectData, reading uses CryptUnprotectData, both under the current Windows user, with app-specific optional entropy (pwsafe-rs/dpapi/v1) so ciphertext stolen from the vault is useless in another application's context. CRYPTPROTECT_UI_FORBIDDEN is passed so a console program can never block on UI it has no way to show.

DPAPI allocates its output with LocalAlloc, which sets the memory-handling rules. The result is copied into a Zeroizing<Vec<u8>>, the DPAPI buffer is zeroized before it is released, and the allocation is freed exactly once with LocalFree. Every one of those steps is a place where plaintext could leak into a heap page that outlives the call.

Tests pin the properties I actually care about: a round-trip returns the original bytes, flipping a single bit of ciphertext fails, and protecting with one entropy value and unprotecting with another fails. DPAPI is doing the work, but the test suite is what proves the wrapper around it is not quietly defeating it.

The clipboard is the delivery mechanism

Secrets are never printed to stdout or stderr, so the clipboard is not a convenience. It is the only output channel, and it is a hostile one: anything running as the same user can read it, and Windows keeps a history and syncs it to the cloud by default.

add and get copy with clipboard history (Win+V) and cloud sync excluded, then wipe after --clear-secs seconds (default 15, maximum 86400) — but only if the clipboard still holds the secret. The check is GetClipboardSequenceNumber, a per-window-station counter: capture it after the copy, sleep, and compare. If the number moved, you copied something else and pwsafe leaves it untouched. If the counter is unavailable, it falls back to reading the text back — zeroized — and comparing. Ctrl+C during the wait keeps the secret on the clipboard. When the state cannot be verified, it refuses to wipe and says so rather than guessing.

Secrets never come from argv

Command-line arguments are visible to other processes and end up in shell history, so set never takes a secret as an argument. At a terminal you get a hidden prompt with a confirmation entry; otherwise one line is read from stdin. Piped input is parsed strictly: a trailing \r\n, \n, or \r and a UTF-8 BOM are stripped, while NUL bytes, invalid UTF-8, more than one line, empty input, and oversized input are rejected. The byte gate (16 KiB) is applied before the input is buffered, and the character limit (4096) is checked after decoding, so a hostile pipe cannot make pwsafe allocate without bound.

Hiding input is itself a console API exercise. Echo-off is a SetConsoleMode change, which means a Ctrl+C during the prompt can leave the terminal in a broken state. pwsafe captures the original mode with GetConsoleMode, registers a handler with SetConsoleCtrlHandler, and restores it both in the handler and when the guard drops. It is a small detail that makes the difference between a hidden prompt and a terminal that echoes nothing afterwards.

The vault file is where the Windows gotchas live

Writes are atomic: a uniquely named temp file created with create_new, flushed with sync_all, then ReplaceFileW onto the vault. That last API matters because it preserves the destination's ACLs; a plain rename does not. Read-modify-write cycles are serialized with a blocking LockFileEx on a sibling .lock file, so two concurrent invocations cannot lose an entry. A vault that fails to decrypt is never treated as empty and never overwritten, because "corrupt" and "new" must not lead to the same code path.

The vault path itself is validated: absolute, on a local drive, with UNC and device prefixes and reserved device names rejected. DPAPI protects the bytes, not where you were tricked into writing them, and a path is untrusted input like any other.

Keys that cannot spoof the terminal

Entry names are restricted to 1–128 printable ASCII characters, which is a security rule rather than a style one. ANSI escape sequences in a key would let stored names repaint the terminal during pwsafe list, and Unicode bidi characters would let one name render as another. Refusing both means the list output is what it looks like.

What it does not protect against

The threat model is written down in the README because the honest list is short and specific: other processes running as the same user (malware, or anything reading the clipboard while the secret is on it), administrators and SYSTEM, offline attacks by someone who can extract your Windows credentials, clipboard entries created before history exclusion or by other tools, and loss of the Windows profile. Security software that promises more than this is usually describing a different threat than the one you have.

Testing

Unit and property tests are the backbone: proptest cases assert that the stdin parser and the vault path validator never panic, and that every accepted input satisfies its invariants (no line breaks, within the byte budget; absolute, local, non-reserved paths). DPAPI has its tamper and entropy tests, and the clipboard delay bounds are tested at the edges (0 and 86400 valid, one past invalid).

CI runs the standard Rust gates — cargo fmt, clippy with warnings denied, cargo test — plus cargo deny pinned to x86_64-pc-windows-msvc, which denies yanked, unmaintained, and unsound crates, unknowns sources, and duplicate versions. Custom semgrep rules block what a password safe should never do: direct printing, process spawning, environment mutation, and file writes outside vault.rs.

Trade-offs

Windows-only, single-user, and no recovery: if the profile dies, the vault dies with it. In exchange there is no master password to forget, lose, or reuse, and no plaintext ever touches the disk or the terminal. For a personal machine where the Windows account is already the thing you defend, that is the right side of the trade.
