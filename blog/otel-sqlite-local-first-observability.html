Local-first observability with otel-sqlite

September 10, 2026 · 3 min read

Observability tooling is easy to set up and even easier to overpay for. For side projects, labs, and small services, a managed platform is often more infrastructure than the problem needs. I wanted the standard OpenTelemetry pipeline — OTLP in, structured logs out — with a sink I could inspect with plain SQL. That idea became otel-sqlite.

What it does

otel-sqlite receives OpenTelemetry log records and writes them to a local SQLite database. Because the data lands in a single file, you can query it with anything that speaks SQL — the sqlite3 CLI, DuckDB, or your own tooling — and back it up by copying one file.

Why SQLite

SQLite is a remarkably good fit for append-heavy log storage:

  • No server to run, no ports to expose, no connection strings to manage.
  • WAL mode keeps reads fast while writes stream in.
  • Retention is a single DELETE statement, and archival is a file copy.

That makes it a natural fit for local development, self-hosted services, audit trails, and air-gapped environments where sending telemetry off-box is not an option.

Trade-offs

This is deliberately a single-node tool. It is not a replacement for a production observability platform: there is no clustering, no dashboards, and write throughput is bounded by one disk. If you need to slice terabytes of traces across a fleet, use a platform built for that. If you need to answer "what happened on this box last Tuesday?" without leaving the terminal, a file is hard to beat.
