Local-first observability with otel-sqlite

September 16, 2026 · 6 min read

I built otel-sqlite to learn two things properly: Rust and the OpenTelemetry Protocol. The idea was small: take OTLP log records over gRPC and write them to a local SQLite file. That was enough to force real concepts instead of tutorials.

The spec, briefly

The spec lives on the OpenTelemetry site. In short, an export request is a ResourceLogs → ScopeLogs → LogRecord tree. I mapped the resource level to a log_resource row (service, host, schema URL, attributes as JSON) referenced by log_event.resource_id, denormalized scope name/version onto the event row, and flattened record fields into columns: timestamps, severity, trace/span IDs as blobs, body and attributes as canonical JSON.

Indexes cover the known query paths: timestamp_ns for time ranges and retention, (resource_id, timestamp_ns) for per-service windows, and a partial (trace_id, timestamp_ns) index for trace lookup. Search runs on a contentless FTS5 table (logs_fts) kept in sync by insert and delete triggers, so new logs are searchable immediately and retention prunes leave no stale entries. A logs view joins event and resource for ad-hoc SQL.

What I took away

OTLP is a service contract before it is a data format. Three gRPC services exist (logs, traces, metrics), each with an Export RPC, and a server must answer UNIMPLEMENTED for the ones it does not serve instead of faking success. I serve logs only. OK means the server took responsibility for the data, but the spec stops short of promising durability, so I defined that myself: a successful export means every record has committed to SQLite before the response goes out.

The second lesson was AnyValue, the oneof behind bodies and attributes: string, bool, int, double, bytes, array, or nested key-value list. The lazy mapping stringifies all of it, which quietly turns numbers into text and arrays into unqueryable blobs. I store structured values as canonical JSON instead: sorted keys, hex-encoded bytes, non-finite doubles as null. Anything that still cannot be represented is either rejected or counted as an explicit loss, never silently converted.

Trace and span IDs have strict rules: 16 and 8 bytes, and all-zero means invalid. Zero-filling a malformed ID would invent a correlation that can never match a trace, so a bad ID rejects the entire request with INVALID_ARGUMENT, giving the sender a loud failure it can fix instead of a silent bad join.

That works only because admission is all-or-nothing. OTLP defines a partial_success field, but partial acceptance plus retries duplicates records, and there is no dedup key. So a request is either admitted completely or not at all: ingress reserves capacity for every chunk before issuing commit tickets, and a full queue returns UNAVAILABLE with nothing accepted. Success and nothing-happened are the only outcomes.

What I learned in Rust

The single writer comes from SQLite, not Rust. Only one writer may hold the database, so writes have to funnel through a single owner. What Rust added was enforcement: Connection is Send but not Sync, so sharing it across tasks does not compile without a mutex, and a mutex on the hot path would just serialize on contention. Moving the connection into one thread and passing owned command messages over a channel makes the ownership transfer itself the concurrency model. Where sharing is genuinely needed (the admission gate every sender clone uses), it is an explicit Arc<Mutex<()>>, impossible to miss.

Every hop between stages is bounded and enqueue is non-blocking. A full queue is not an internal error to spin on; it is a signal that the writer is behind, and it reaches the client as UNAVAILABLE. The alternative, an unbounded queue, hides overload until memory pressure turns it into an outage, and the depth reading stops meaning anything. A bound turns "how loaded is this thing?" into a number I can watch.

gRPC ingress runs on a tokio multi-thread runtime because requests are IO-bound and numerous, while the writer is synchronous rusqlite on a dedicated blocking thread. Mixing the two is deliberate: async buys concurrency at the edge, and blocking keeps the single writer simple and avoids async scheduling inside the one place where every microsecond is throughput. The subtle part (an admission gate around a crossbeam channel shared with async producers) is confined to the ingress crate, so the rest of the pipeline stays on one model.

rusqlite exposes SQLite's error codes, and they map almost directly onto a failure policy: BUSY/LOCKED is retryable with backoff, constraint and binding failures are poisonous to a specific row, and everything else is fatal and should fail loudly rather than be guessed at. Encoding that as an enum means classification happens once, in one place, and each class has defined behavior instead of a match arm repeated at every call site.

How I designed it

OTLP gRPC → bounded ingress queue → insert batcher → bounded command queue → single SQLite writer (WAL) → SQLite

Exactly one component owns the SQLite connection. Ingress turns OTLP into log rows, the batcher groups inserts, and the maintenance worker schedules retention and checkpoints. All of them are just producers of the same bounded command queue. That gives every write a total order, removes lock contention from the hot path, and turns invariants like "retention never races an insert" into a property of the shape instead of a rule to remember.

Both queues are bounded and admission is all-or-nothing, so backpressure reaches the client as a retryable status instead of an OOM inside the process. Nothing buffers without limit: not the channel, not the batcher, not the WAL. When a limit is hit, the failure is visible at the edge where it can be acted on, not discovered later in a memory graph.

A successful export means committed. Each accepted chunk gets a commit ticket, the writer publishes a contiguous watermark as transactions land, and the handler holds the response until the watermark passes its highest ticket. If the writer or batcher dies, the ledger closes and pending acknowledgements fail fast with UNAVAILABLE instead of hanging. A faster mode that acknowledges on admission exists, but it can lose records in a crash. The trade is named and configurable, not hidden.

Failures are classified, not improvised. Retryable transactions re-attempt four times with exponential backoff; a batch poisoned by one bad row is re-run in tolerant mode, so healthy rows commit while offending ones are dropped and counted; a fatal error kills the writer, fails every pending acknowledgement, and lets a supervisor restart. In all three paths the rule is the same: an acknowledgement is only ever sent for data that is actually on disk.

WAL mode is what makes the single writer cheap. A commit is an append plus a lock operation rather than an fsync per transaction, so the writer is mostly CPU-bound and readers see a consistent snapshot without blocking. Retention is a batched DELETE that garbage-collects orphaned resources, checkpoints keep the WAL from growing without bound, incremental vacuum returns freed pages without rewriting the file, and backup is a file copy.

Testing

A service that promises durability is only as good as the tests that try to break it, so most of the effort went here. The integration tests never mock the pipeline: they boot exactly the wiring of the production binary, drive real OTLP/gRPC over TCP, and then query the SQLite file to validate what landed. The same harness checks backpressure semantics, asserting that a full queue returns UNAVAILABLE for the whole request and that a retried request produces zero duplicate rows.

Durability is tested against process death, not just shutdown. One test boots the real binary under closed-loop load, kills it mid-WAL-write, restarts on the same database, and validates. Writer and batcher death are tested independently through environment-gated fault knobs that make each thread exit through its real fatal path. A container-level test docker-kills the sidecar mid-load and restarts on the same volume, and a backup/restore suite runs against the release binary.

Two cargo-fuzz targets cover the untrusted-input boundary: one fuzzes the batcher and commit ledger, the other pushes arbitrary bytes through the OTLP export handler (protobuf decode, validation, mapping, enqueue). The invariants are explicit: decodable input must never panic, a rejected request surfaces as INVALID_ARGUMENT rather than an abort, an accepted request never carries partial success, and nothing is enqueued for a rejected one. The seed corpus covers malformed trace and span IDs, deeply nested bodies, unknown severity values, and every AnyValue kind.

CI runs the boring things on every change: rustfmt, clippy with warnings denied, the full test suite, cargo-deny for licenses and advisories, cargo-audit, and semgrep rules. It also runs the release-binary crash and backup/restore suites, a fuzz smoke pass, and the backpressure correctness scenario. A longer fuzz run is scheduled nightly. The whole workflow is runnable locally through act, so I can reproduce CI before pushing.

Performance has its own harness: an end-to-end client that drives real gRPC through the complete production pipeline and validates the database afterwards, plus Criterion microbenchmarks for mapping, batching, queueing, and transactions so regressions show up per component. Release-mode runs are enforced (a dev build needs an explicit flag), and the published numbers come from the real binary on a real disk, not a tmpfs or a mock.

For reference, on a Windows dev machine (release build, WAL + synchronous=NORMAL), the baseline scenario held the full 1,000 records/s offered for 60 seconds: 60,000 of 60,000 rows present, zero duplicates, and acknowledge latency p50 29 ms / p99 85 ms while waiting for durable commits. The write path benchmark reaches about 180,000 records/s at 1,000-record transactions, with a marginal cost of roughly 5.7 µs per record, and the entire ingress-to-writer path adds under 2% on top at production batch sizes. In a 100,000 rec/s offered ramp, the ingress queue peaked at 11 of 50,000 chunks, so the closed-loop client ran out of concurrency before the writer ran out of capacity. Both runs, with exact revision and configuration, are committed under results/ in the repo.

Trade-offs

Deliberately single-node: no clustering, no dashboards, throughput bounded by one disk. If you need to slice terabytes across a fleet, use a platform built for that. If you need to answer "what happened on this box last Tuesday?" from the terminal with plain SQL, a file is hard to beat.
