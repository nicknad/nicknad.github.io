Local-first observability with otel-sqlite

September 10, 2026 · 3 min read

I built otel-sqlite to learn two things properly: Rust, and the OpenTelemetry Protocol. The idea was small 'take OTLP log records over gRPC, write them to a local SQLite file', but it forced real concepts instead of tutorials.

OTLP concepts

The spec is the hard part. A request is nested: ResourceLogs → ScopeLogs → LogRecord, where the resource and scope carry metadata that applies to every record under them. Body and attributes are AnyValue, a oneof that can nest arrays and key-value lists. Trace and span IDs are raw bytes with strict validity rules, and severity is an enum with unspecified values.

What I took away:

  • OTLP's service contract: which RPCs to serve, what 2xx guarantees, what UNIMPLEMENTED means.
  • How to preserve AnyValue without silently converting it — structured bodies become canonical JSON.
  • Why malformed trace/span IDs should reject a whole request instead of being zero-filled.
  • All-or-nothing admission: a retried request must never duplicate records, so there is no partial success.

What I learned in Rust

  • Ownership across threads: sharing a connection is impossible, so the type system pushes you toward one writer owning it.
  • Bounded channels and backpressure beat unbounded queues, the queue depth becomes a load signal, not a memory leak.
  • Blocking vs async: the writer stays on a blocking thread while ingress runs on tokio; mixing them is a design choice, not an accident.
  • rusqlite error codes map cleanly onto retryable, poisonous, and fatal failure classes.

How I designed it

OTLP gRPC → bounded ingress queue → insert batcher → bounded command queue → single SQLite writer (WAL) → SQLite
  • Single writer. Exactly one component owns the connection. Everything else produces commands.
  • Bounded queues everywhere. Full queues return UNAVAILABLE so clients retry; nothing hangs.
  • Durable acknowledgements. A 2xx means committed: each accepted chunk gets a commit ticket, and handlers wait on the writer's contiguous watermark.
  • Error classification. Retryable errors back off; poisoned rows are quarantined while healthy rows commit; fatal errors fail pending acks fast instead of silently dropping data.
  • WAL mode. Reads stay fast while writes stream in; retention is one DELETE, backup is a file copy.

Trade-offs

Deliberately single-node: no clustering, no dashboards, throughput bounded by one disk. If you need to slice terabytes across a fleet, use a platform built for that. If you need to answer "what happened on this box last Tuesday?" from the terminal with plain SQL, a file is hard to beat.
